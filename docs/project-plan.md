## 1. 目标与时间依据

**暂定题目：面向 openEuler 的 CPU 配额行为验证与性能回归测试工具。**

首版固定一个 openEuler 版本、x86-64 虚拟机、单进程单线程的 CPU 计算负载，完成环境检查、配额配置、重复运行、原始数据记录、行为检查和历史结果对比。系统版本与 Python 版本在 10 月 25 日前统一记录，不能仅写“最新版”。

时间依据：用户提供的《2026年操作系统设计赛华东区域赛章程-1010.pdf》第 2 页明确写明报名及作品提交截止为 **12 月 24 日**；评审为 12 月 25—31 日，决赛答辩安排在一月中旬，具体以组委会公布为准。

2026-10-21 查询的 [应用开发赛道平台](https://course.educg.net/pages/contest/contest.jsp?contestCID=0&contestID=fLzatL8sv4E&doVisit=true&my=false) 同时显示“10/15 09:17—12/24 23:59”和“结束 02/01 23:59”。后者的含义尚未核实，不能当作提交延期通知。因此本计划按 **12 月 24 日截止、12 月 20 日完成正式提交** 倒排；队长在 10 月 25 日前向赛事方核实具体提交入口和时间。

### 首版范围

- 一个可校验计算结果的 C 测试程序，使用固定输入／工作量；具体工作量先做小规模试验再确定。
- 三种配置：本次运行未主动施加配额、约半个 CPU 的配额、约四分之一个 CPU 的配额。具体周期和配额值在环境验证后记录。
- Python 命令行执行器，记录实际耗时、CPU 时间、资源组统计、退出状态和环境信息。
- CSV/JSON 原始结果、汇总表、离线 HTML 报告。
- 同配置、同输入、兼容环境下的历史基线比较；区分行为测试与跨版本性能比较。
- 处理超时、权限不足、运行失败、缺失指标及清理失败，允许输出“无法判断”。

“未主动施加配额”不等于系统完全没有限制，仍需检查可见的父级约束。CPU 配额是上限，不能要求所有环境中耗时精确翻倍。跨机器结果用于独立复现和解释环境差异，不能直接混入同一性能基线。

父级配额、共享资源组、多进程和后台竞争可作为后续扩展场景；首版应至少能识别不满足测试前提的环境。内存、磁盘、网络和自动调优暂不纳入首版。

## 5. 模块边界与协作接口

| 模块建议路径 | 负责人 | 边界 |
|---|---|---|
| src/runner/、src/collector/ | 队长 | 环境、配额、运行、采集、清理；输出统一数据 |
| workloads/、tests/、experiments/ | 队员 1 | 可校验负载、正常异常场景、复现与原始实验记录 |
| src/report/、docs/、demo/ | 队员 2 | 读取数据生成报告、使用说明、演示材料 |

这些是建议结构，目录尚未全部创建。字段约定应在 10/28 前完成，队员 2 可先使用标明 synthetic 的样例开发；正式测试只使用实际采集数据。

最少字段建议：schema_version、run_id、数据来源标记、环境指纹、程序版本、输入／工作量、配额配置、可见父级约束、实际耗时及单位、CPU 时间及单位、资源组统计差值、退出码、运行状态、错误原因。原始数据与汇总结果分别保存；指标缺失用 null 并说明原因，不能写成 0。

性能比较需区分固定条件和变更对象：输入、资源配置、采样方法及环境应兼容；若测试程序版本本身是变更对象，必须明确记录旧／新版本和相同功能输出校验。不能因版本变化就一律禁止比较，也不能把不同负载工作量直接比较成“性能提升”。

## 6. 验收与记录方式

- 每周一次约 20 分钟同步，可固定周日；每人报告已完成证据、阻碍和下一步。
- 每个任务附代码／文档链接、运行方式、实际结果与已知问题；AI 生成部分由负责队员运行和解释，并保留使用记录。
- 队员 1 验证队长执行器；队员 2 核对队员 1 的数据与单位；队长检查报告和集成。三人均能独立运行完整演示。
- 小规模试做可先重复 5 次观察波动；正式实验重复数根据耗时和波动确定，不能仅凭“重复了 5 次”宣称统计显著。
- 基线比较应保存完整分布或每次结果，并明确规则阈值的依据；阈值设定与验收样本尽可能分开，样本不足或环境不兼容时不给确定结论。
- 11/08 起用可复现演示与问题清单辅助导师沟通；每人撰写自己模块的设计、测试和限制说明，队长负责整合。
- GitHub 为团队协作主仓库；按赛事要求尽早建立官方 GitLab 开发与同步流程。若前置报名条件阻碍，应在 10/28 节点记录并推动解决，保留真实提交历史，不等最后一天集中上传。
