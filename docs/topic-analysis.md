# 赛道 2 可选选题、各维度分析与综合评价

版本：v1.0 · 日期：2026-10-20 · 状态：供三名队员共同讨论，尚未定题

## 1. 阅读结论

优先考察以下三个方向：

1. **系统性能实验与回归测试：整体最均衡。** 容易把功能、实验数据和教学价值组织成可验证成果。
2. **特定系统故障诊断：系统深度更强。** 要付出更多精力验证因果判断和误报边界。
3. **环境与服务启动诊断：较快形成初稿。** 需要从简单错误匹配深入到证据检查与修复验证。

小型软件移植与优化作为条件候选：只有找到真实、范围可控的兼容问题后，才能判断是否值得做。

以上排序依据团队适配性和交付风险，不代表官方评分，也不能用于推算获奖概率。各题目是基于官方范围提出的候选名称，不是官方独立命题。此前的 EulerLens 方案只对应方向 B，**没有自动成为团队最终决定**。

### 2.2 本团队的选题假设

- 三人，大二阶段，操作系统项目经验有限。
- 有 C 基础，一名队员有一些 C++ 基础，三人都有少量 Python 基础。
- 计划大量使用 AI 辅助开发，但每周投入时间尚不固定。
- 已有虚拟机和 16GB／32GB 内存电脑；必要时可考虑租机器。

## 4. 候选方向详析

### A. 系统性能实验与回归测试工具

**示例题目：面向 openEuler 的进程资源限制行为与性能回归测试工具。**

让同一个程序在不同 CPU 配额、并发数或系统配置下重复运行，记录环境与指标，发现行为异常或性能退化。首版只选择其中一个维度。

- **优点：** 大部分可以用 Python 完成；少量 C 测试负载便于解释；容易形成数据、图表、实验指导和可重复演示；分工边界清楚。
- **缺点：** 简单调用现有基准测试并生成图表，贡献不足；测试平台范围容易越做越大。
- **技术难点：** 控制缓存、预热、宿主机负载与后台任务；确定测量单位和采样窗口；区分自然波动与真实性能退化；处理超时和失败后的清理。
- **最小初稿：** 固定一个系统版本，一个负载类型，三种配置；重复运行；保存原始数据和环境；输出对比报告。
- **验证方式：** 用已知资源配置改变构造正例，用重复相同配置构造负例；报告波动、误报及失败次数；在另一名队员的环境复现。
- **可能的贡献：** 针对某类资源约束建立测试集，提供可解释的判定和环境差异检查。必须先比较已有工具，不能预先认定创新。
- **同类边界：** openEuler 已有 mugen 等测试基础设施；可复用其思想或组件并披露，重点说明新增覆盖与判断能力。[S3]
- **综合评价：** 当前最均衡；适合时间不固定、先完成一个可靠小作品的团队。

### B. 特定系统故障诊断工具

**示例题目：EulerLens——面向 openEuler 的 CPU 配额受限诊断与实验复现工具。**

围绕“整机 CPU 看似有空闲，程序为什么仍然慢”，采集进程及资源组证据，检查配额、节流和竞争等现象。

- **优点：** 问题具体；系统相关性强；可形成制造问题、定位证据、调整配置、验证变化的演示过程。
- **缺点：** 指标采集容易，准确解释难；多种原因同时出现时容易误诊；已有性能分析工具竞争较强。
- **技术难点：** 资源组包含多个进程；父级限制仍会生效；进程退出、PID 复用、组迁移影响采样；缺少权限或信息时应输出不确定；组级证据不能直接归因到某一个 PID。[S6]
- **最小初稿：** 只分析 CPU 配额及少数混淆场景；输出原始证据、判断依据与局限；不扩展到磁盘、内存、网络全覆盖。
- **验证方式：** 构造直接配额、父级配额、无配额但存在竞争、混合原因等样本；诊断程序不能读取实验标签；独立统计误报、漏报、不确定比例和采集开销。
- **可能的贡献：** 特定场景的证据关联、混淆场景区分及可复现案例；需要同类实测支持。
- **同类边界：** oeAware 已有采集、分析结论和调优建议，不能把“采集＋报告”当成独有能力。其是否覆盖拟做的具体配额诊断，需要安装验证，当前未下结论。[S2]
- **综合评价：** 研究与答辩深度较好，但要求至少一名成员深入理解指标及限制层级。原 EulerLens 草案仍为候选，尚未实施。

### C. 环境与服务启动诊断工具

**示例题目：面向 openEuler 的 Python/C 应用启动失败诊断助手。**

定位固定部署方式下的依赖缺失、动态库缺失、权限不足、端口占用、服务配置错误等问题。

- **优点：** 使用场景直观；容易构造故障和验证修复；Python 适配好；较快形成可给老师展示的初稿。
- **缺点：** 容易停留在报错关键词匹配；为不同程序增加规则可能变成重复劳动。
- **技术难点：** 相同报错可能有不同原因；日志缺失或权限不足；解释器与实际运行环境不一致；动态库、服务依赖和启动顺序需要分别理解。
- **最小初稿：** 一种应用部署方式、约五类故障；每类输出检查项、证据、建议及验证命令。建议先只读检查和手动修复。
- **验证方式：** 为每类错误建立可重建环境，保留健康环境作为负例；测试多个错误并存；验证修复后能否正常运行。
- **可能的贡献：** 由日志提示定位到实际状态检查，再形成明确的验证路径；减少错误建议。需要与人工检查或已有工具比较。
- **AI 使用边界：** AI 可解释已有证据，不应凭日志片段臆测已确认的原因。
- **综合评价：** 适合先做初稿再寻求指导；后续需增加推理可靠性或特定场景覆盖，才能避免作品过浅。

### D. 小型软件移植与优化

**示例题目：某小型 C/C++ 命令行工具在 openEuler 上的适配与性能优化。**

当前尚无已选软件和已确认兼容问题，因此这是方向候选，不是已确定可做的项目。

- **优点：** 原始版本和增量补丁清楚；可用测试与性能对比说明贡献；有机会向上游反馈。
- **缺点：** 软件可能本来就能直接运行，缺乏工作量；也可能陷入复杂依赖、构建系统和架构问题。
- **技术难点：** 库版本、二进制接口、构建工具、路径及权限差异；性能优化不能破坏功能；要明确原项目许可和贡献来源。
- **最小初稿：** 同一 CPU 架构上的一个小型工具，修复一个真实兼容问题，提供构建、安装与测试脚本。
- **验证方式：** 保存修复前失败记录；修复后执行功能测试；有性能优化时固定数据与配置重复测量。
- **筛选门槛：** 原项目活跃程度、许可、依赖规模、测试可用性、问题能否复现；无法说明真实问题时不立项。
- **同类边界：** x2openEuler 属于已有迁移工具体系；小型应用适配与整个系统迁移不是同一任务，不能直接混为同类性能比较。[S5]
- **综合评价：** 找到合适对象后可能很划算，目前证据不足，不排在前三个已具体化的方向之前。

### E. 进程资源管理与任务运行工具

**示例题目：面向共享实验机的轻量任务运行与资源管理器。**

支持任务排队、CPU／内存限制、超时终止和结果记录。首版单机、单用户、可信任务。

- **优点：** 系统机制明确；任务失控前后的对比容易展示；可服务于课程实验或小型批处理。
- **缺点：** 系统服务管理器和容器工具已提供许多基础功能；需要突出具体场景的便利性或可靠性。
- **技术难点：** 取消时处理整个进程树；工具崩溃后的恢复；并发状态一致性；权限、资源组创建和清理；资源限制不等于完整安全隔离。
- **最小初稿：** 队列、运行记录、一个资源限制和超时处理，任务失败后可清理。
- **验证方式：** 子进程、超时、取消、执行器异常退出、资源耗尽等场景；检查是否有残留任务或错误状态。
- **可能的贡献：** 针对教学批任务形成透明资源记录和可靠恢复流程。
- **综合评价：** 系统深度足，但可靠性工作较多；不要扩展为运行任意不可信代码的在线判题安全平台。

### F. 文件备份、版本管理与恢复

**示例题目：面向实验目录的增量备份与恢复验证工具。**

- **优点：** 用户需求容易理解；版本恢复、空间开销和数据校验容易演示；可使用 Python。
- **缺点：** 现有工具成熟；普通复制加界面差异小；备份成功不代表能正确恢复。
- **技术难点：** 备份时源文件变化；符号链接和权限；中断、磁盘满、索引损坏；恢复路径和内容一致性。
- **最小初稿：** 限定普通文件目录；版本记录、内容校验与恢复验证；明确未支持文件类型及一致性边界。
- **验证方式：** 修改、删除、重复内容、中断和空间不足；逐文件校验恢复内容；不使用真实重要文件进行破坏性实验。
- **同类边界：** restic 等工具已有丰富备份能力；应选择具体使用场景的不足进行对比。[S7]
- **综合评价：** 初稿直观，但可靠性与差异化都不轻松，优先级低于 A/B/C。

### G. 安全配置检查

**示例题目：面向教学实验机的安全配置审计与证据报告工具。**

- **优点：** 可从有限规则开始；健康与错误配置容易构造；便于逐条开发和验证。
- **缺点：** 规则堆积不等于技术贡献；成熟工具覆盖广；缺少安全知识时易写出错误规则。
- **技术难点：** 配置是否危险取决于使用场景；修复后的软件版本可能含安全补丁，不能只按版本号推断漏洞；误报和漏报都需核对。
- **最小初稿：** 固定系统版本与使用场景；有限只读规则；每项列明证据、适用条件和例外。
- **验证方式：** 每条规则至少有健康、错误和不适用案例；核验报告与真实配置一致。
- **同类边界：** OpenSCAP 已提供安全配置评估能力；需要比较具体覆盖、部署便利性或解释方式。[S8]
- **综合评价：** 有安全兴趣或指导资源时考虑；通用漏洞挖掘与自动漏洞利用不作为起步目标。

### H. 真实操作系统实验教学工具

**示例题目：基于真实 Linux 资源控制的可复现实验工具。**

- **优点：** 帮助队员学习；演示直观；可对接教学价值这一评分维度。
- **缺点：** 纯算法动画系统贡献较薄；重做完整 OS 课程实验更接近赛道 1 的描述，需要注意选题边界。
- **技术难点：** 真实系统现象受环境影响；实验失败时如何解释；可视化不能把理想模型当成实际行为。
- **最小初稿：** 一个真实系统机制、两三个可执行实验、原始数据、解释和复现说明。
- **验证方式：** 另一台机器独立复现；区分理论预期、实际观察和偏差原因；收集真实试用反馈，不能虚构教学效果。
- **可能的贡献：** 将资源配置、实际状态、测量结果与机制解释关联。
- **综合评价：** 最适合作为 A/B 的教学使用模式；首版不同时建设账户系统、课程管理和大型网站。

## 5. 暂不作为主攻方向的选项

| 方向 | 为什么暂不优先 | 可保留的小切口 |
|---|---|---|
| eBPF 深度追踪／通用调试器 | 内核事件、验证器、权限、并发和版本兼容门槛较高 | 后期加入一个明确用途的采集功能 |
| AI 自动调优 | 性能评价与搜索成本高，容易把噪声当提升；已有 A-Tune | 固定负载和单个参数的可重复对照实验 |
| 系统模拟器 | 简化演示易做，但正确且有用的模拟需要体系结构知识 | 有导师支持时选择极窄模块 |
| 通用 AI 运维助手 | 对话演示容易，诊断准确性与执行可靠性难证明 | 为确定性检查结果提供解释 |
| 普通管理网站／聊天应用 | 可以属于应用开发，但需要证明目标系统相关贡献 | 围绕明确系统特性设计一个小功能 |

技术资料见 A-Tune [S4] 与内核 BPF 文档 [S9]。以上为团队适配性判断，不是赛事禁止范围。

## 6. 如何形成有说服力的参赛作品

不要把 UI、生成报告、调用 AI 或“支持 openEuler”单独当成创新。每个候选都要回答：

1. 具体用户是谁，在哪个场景遇到什么问题？
2. 现有工具如何处理，有什么可复现的不足？
3. 本队新增了哪些代码、规则、测试或适配？
4. 如何证明有效，哪些场景会失败或不能判断？
5. 另一名队员能否按 README 独立复现？

允许复用成熟组件，但必须说明来源、许可、使用目的和本队增量。比较时使用相同场景与输入，不挑选不合理的弱基线。

AI 辅助应分小步进行：先写预期与测试，再生成实现，随后由队员运行并解释结果。编造实验数字、复制没有核对的引用、无法解释核心代码，都不能由“AI 辅助”合理化。

## 7. 选题验证与综合决策

### 7.1 先筛选，再小范围试做

每名队员先独立阅读并填写评价表，选出两个候选，再共同确定一个首选和一个备选。不建议八个方向同时开工。

对首选安排约一周的可行性验证；实际投入取决于课程安排，这不是完成参赛作品的工期承诺：

- 能否搭建统一环境并运行一个完整场景？
- 能否构造健康与异常两类结果？
- 是否存在一个值得比较的现有工具？
- 是否能指出自己的增量贡献？
- 能否由第二名队员从零复现？

若只完成界面而不能解释底层证据，或长期卡在依赖安装，应缩小范围或切换备选。

### 7.2 讨论用评价维度

| 维度 | 讨论问题 |
|---|---|
| 兴趣与持续投入 | 是否愿意连续研究这个问题，最低周投入是多少？ |
| 知识可掌握程度 | 三人能否理解核心机制并回答追问？ |
| 正确性可验证程度 | 是否知道正确答案，能否重复制造场景？ |
| 增量贡献 | 与同类方案相比，具体增加什么？ |
| 可交付性 | 最小版本能否独立成立，有哪些依赖？ |
| 分工与复现 | 三人都有实质贡献吗，能交叉检查吗？ |
| 文档与演示 | 能否形成有证据的报告和稳定演示？ |
| 后续指导 | 能否带着明确问题找老师，而非只展示功能清单？ |

不设虚假的精确总分。尚无实测证据的维度标注“待验证”，避免平均分掩盖关键阻碍。

### 7.3 当前综合建议

- **以完成稳定作品为主要目标：优先 A。**
- **愿意深入系统机制、有人承担诊断正确性：优先 B。**
- **希望尽快形成可展示初稿：优先 C。**
- **发现真实、范围明确的兼容问题：重新评估 D，可能提高优先级。**
- **H 可作为 A/B 的教学场景；E/F/G 暂作第二梯队。**

初期使用已有虚拟机即可验证上述小范围方案。先记录虚拟机、内核、资源分配及宿主机负载，再决定是否需要额外机器；租机器不能替代实验设计。尚未确定最终系统版本、题目、导师或开发排期。
