# 答辩讲解与常见问题

日期：2026-11-17。配套 [十页答辩初稿](presentation/答辩初稿_20261117_v1.pptx)，逐页讲解要点及来源在 PPT 备注中。它是工作稿，尚未核验最终答辩时长/形式。成员姓名、实际分工和人工贡献由团队填写，不根据模块角色推测。

## 约一分钟的项目介绍

这个项目面向固定 Linux 环境中的数据处理任务。我们用固定种子生成 CSV，执行单进程分组聚合，再用 SQLite 独立核对输出。在结果正确的前提下，工具控制 CPU 时间上限，重复执行并保留实际控制值、耗时、退出与清理证据。报告区分不同配额的配置对照，以及同资源、兼容环境下的历史比较。当前历史规则只给出探索性的复核提示和无法比较原因。已有 openEuler 代理实测与可追溯原始记录，人员交叉复验和更广统计验收仍待完成。

## 常见问题

### 1. 为什么选择分组聚合？

输入、分组 count/sum 语义和正确输出容易固定，适合先验证 CPU 配额与测量流程。当前采用单进程，减少并行度、外部数据库服务与网络带来的额外变量。这个场景不能代表所有数据处理业务。

### 2. 固定随机种子就足够复现输入吗？

还需固定生成器版本、行数、请求组数与字节内容。本项目记录这些参数，并以完整 CSV 的 SHA256 构成 input_id。源码哈希和运行参数构成 workload_version。

### 3. 如何证明结果正确？

被测程序使用 Python 字典逐行累计，参考实现把同一输入导入 SQLite，执行独立 GROUP BY/COUNT/SUM。每份 stdout 必须符合参考结果的规范字节，校验记录绑定 run_id 和 stdout 哈希。还有带负值的手算样本。正确性证据只覆盖当前任务与测试范围。

### 4. 为什么 stdout 哈希一致还不够？

两个版本可能输出相同的错误结果。哈希可以证明字节相同，不能证明算法语义正确，所以仍需独立参考结果。

### 5. 100% 配额是什么含义？

是一个逻辑 CPU 的时间上限，不是整台机器的满算力。程序读取服务内实际 cpu.max 核验，而不是只根据请求值宣称配额生效。

### 6. null 是否意味着完全不受限制？

只表示本工具没有设置本地配额。父级 cgroup、宿主机或虚拟化调度仍可能限制任务，工具会保存可见父级信息，但看不到的约束不能据此排除。

### 7. 为什么 50% 不一定精确慢一倍？

配额是上限，实际耗时还受到周期、节流、进程启动、I/O、缓存、等待与宿主机调度影响。本次表格只说明实测趋势，不承诺固定倍数。

### 8. wall、CPU 与 cgroup CPU 统计有什么区别？

wall 是 worker 中既定单调计时区间的秒数，包含区间内快照保存、进程启动、等待回收与末次采样开销。CPU 时间是已回收子进程的 user+system 秒。cgroup 的 usage_usec 等为组内微秒差值，含 worker 区间开销。它们不能直接互换。

### 9. 为什么本队和 GNU time 的数值不完全相同？

计时边界、输出精度和采集步骤不同。原生对照也需要脚本补齐快照、循环、校验和清理检查。现有数据可以对照量级与趋势，不能将差值直接解释成某种机制的净开销或工具速度排名。

### 10. 为什么预热与测量要分开？

预热可以减轻部分首次启动/缓存影响，仍不能证明环境完全稳定。预热保留原始记录，但不进入常规性能汇总。每档五次或每场景七次是初步流程/规则检查，不是统计功效保证。

### 11. 历史比较要满足什么？

成功的真实测量、非预热、清理与配额核验、有效指标、功能正确性、输入和资源/环境兼容、干净可识别的 Git 提交，以及互不重叠的 run_id。负载版本可以变化，因为它正是比较对象，但输出必须保持正确和一致。

### 12. 脏 Git 或不完整实验会怎样？

脏提交不进入已校验常规比较；不完整实验或计划数不一致不能当作完整轮次。失败、未知状态和缺失指标单列原因，不能补零后当成功样本。

### 13. 15% 阈值与至少五条样本从哪里来？

是目前预先固定的探索性规则，用于验证比较流程。尚未根据广泛独立样本完成校准，不是通用标准。当前判定为中位数比大于 1.15 才提示复核，等于阈值不触发。

### 14. 没有触发阈值可以说“没有退化”吗？

不能。低于阈值的变化、样本不足或未观察到的波动仍可能存在。当前结果只表示这批可用样本没有触发既定规则。

### 15. “阈值敏感”是不是置信区间？

不是。它只把当前最小/基线最大至当前最大/基线最小作为已观察范围，检查是否跨过阈值。它没有置信水平，false 也不证明统计稳定或显著。

### 16. 已知变慢样本是否是真实业务故障？

是明确设计的验证变体：完整结果不变，额外重复全量或部分输入处理，版本标识包含参数。本轮 5%、15%、25% 是额外工作量比例，不保证相同比例的耗时增长，也不能代表真实线上故障分布。

### 17. 超时、中断和执行器丢失如何处理？

超时、失败和清理失败分别记录。SIGINT/SIGTERM 保存 interrupted 并停止调度。执行器硬终止不能捕获，worker 超时/服务看门狗提供有限寿命兜底，随后通过所有权与同机器/启动周期检查显式 recover，记录 aborted，不改成成功样本。

### 18. 与已有工具相比，新增了什么？

systemd/cgroup 提供资源控制，GNU time 提供计时，SQLite 提供独立聚合。项目新增的是固定场景的编排、正确性绑定、最终记录与原始证据协议、保守前提/拒绝原因，以及离线报告。成熟工具加脚本也能组成类似流程，本项目没有证明独特性或普遍性能优势。

### 19. 29 项测试和 84 次实验分别指什么？

29 是最终诊断源码 25b7f32 的目标机测试数，0 跳过。84 是最近一轮 36 次工具对照加 48 次规则实验，其中 72 条非预热测量、12 条预热排除。它们不能替代前一轮 54 次的版本/输入说明，也不等同非实现者验收。

### 20. 还缺哪些验收？

非实现者复验、更广机器与波动样本、其他完整框架的适用性评估、正式视频/答辩规格和赛事平台核验。已有代理实测不能代替这些事项。团队还需要能解释自己的实际实现、AI 使用和已知局限。
